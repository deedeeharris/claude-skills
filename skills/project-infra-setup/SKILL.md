# Project Infra Setup

Production-first bootstrap. Keep secrets out of terminal output, repo files, chat, and final answers.

> **Maturity.** The Day 0 GitHub path (`bootstrap-repo.ps1`) ran live only against a private Free-plan repo in degraded mode: repo settings, Environments, their variables and `main`-only branch policies were applied and checked; rulesets and Environment reviewers were refused by GitHub on that plan (measured refusals in `references/repo-bootstrap.md` section 0). The success path for rulesets and reviewers (a public repo or a plan that supports them) follows GitHub's REST docs but has NOT been run yet, so prove G1, G3 and G4 on a throwaway repo first. The Terraform/GCP deploy path (sections 5 and 6: bootstrap, plan/apply, preview, drift) passed static validation (`terraform validate`, actionlint) and independent review but has NOT yet run against a live GCP project, so it is EXPERIMENTAL. Run the gate proofs on a throwaway project first and treat any failure as a skill bug.

## Principles

1. **Terraform owns long-lived infra; GitHub Actions only runs it.** Cloud Run services, IAM, Artifact Registry, Secret Manager (containers), buckets, WIF, env wiring: all in Terraform. Actions builds the image and runs Terraform, which ships it (an app deploy is a gated Terraform apply). Ad-hoc `gcloud` is for one-time bootstrap and read-only inspection only.
2. **No apply without a human.** Plan runs on PR (read-only). Apply runs after merge, pauses on a GitHub Environment with required reviewers, and applies the exact saved plan the reviewer saw.
3. **No JSON keys, no shared identity.** Workload Identity Federation (OIDC) only, with an attribute condition. Every environment has its OWN pool, state bucket, planner and applier, each bound to exactly one GitHub Environment, so a dev job cannot hold a prod permission or touch prod state. Terraform is the ONLY writer of the dev and prod Cloud Run services (image and traffic included): an app deploy is a Terraform apply with `-var image=<digest>`.
4. **One trunk.** `main` is the only long-lived branch. Same commit goes dev, then prod. Environments are directories, not branches or workspaces.
5. **"Deployed" needs proof.** Judge the deploy JOB's conclusion, not the workflow run: a skipped job rolls up as green. Prove a deploy by comparing the image digest of the revision that SERVES traffic with the digest that was built, never by timestamps or "a new revision exists". `gcloud run deploy --env-vars-file` replaces the whole env: diff the env vars before any such deploy.

## Prerequisites

`gh` CLI (2.40+, authenticated: `gh auth status`), `gcloud` (with ADC for the Terraform bootstrap), `terraform` (1.11+; match `TF_VERSION`), `git`. PowerShell: Windows PowerShell 5.1 or PowerShell 7+ (`pwsh`; dry run and refusal path tested on 5.1 and on pwsh 7.4 Linux, `-Apply` exercised on Windows only) for `bootstrap-repo.ps1`. Python 3 (standard library only) for `verify-required-checks.py`: `python -I ...`, `python3 -I ...` on macOS/Linux. GitHub plan: private repos need Pro/Team/Enterprise for rulesets and Enterprise for Environment required reviewers (section 2, step 1). A GCP billing account. Full list: `README.md`.

Files: templates in `templates/`; Day 0 detail in `references/repo-bootstrap.md`; security baseline in `references/security-baseline.md`; renaming and pin refresh in `references/customizing-templates.md`; stack-specific modules in `references/optional-modules.md`.

## Workflow

### 1. Inventory
- Confirm goal and mode: PRD/spec only, scaffold only, infra only, or feature work.
- Confirm repo remote, GitHub plan and repo visibility (private repo: rulesets need Pro/Team/Enterprise, Environment required reviewers need Enterprise, Environments + variables + branch policy work on every plan; public repo: all plans; measured table in `references/repo-bootstrap.md` section 0), active gh auth, gcloud account, billing, database account, region.
- Create or update `docs/stack.md` (dated). Record IDs and resource names only, plus "not yet done" items.
- **Refresh pins** before copying any template: `TF_VERSION` in `bootstrap.config.example.psd1`, the action versions/SHAs in the workflow templates, the provider constraint (and later the lock file). Dates under Sources are "last checked": re-check before relying on them. Commands: `references/customizing-templates.md` ("Refresh pins").

### 2. Day 0: repo and CI/CD (before any Terraform)
Detail, exact payloads and proof commands: `references/repo-bootstrap.md`. Templates: `templates/github/`. Do the steps in order; stop at the first failed check.
1. **Plan check.** Never assume the plan: `gh api user` returns NO plan for personal accounts (verified), so ask the operator or read Billing and plans, and write it as `Plan = 'free|pro|team|enterprise'` in the config. Orgs: `gh api orgs/<org> --jq .plan.name`. The script stops on an empty plan and REFUSES (exit 2, before any write) a private repo whose plan lacks rulesets, or any private non-Enterprise repo that asks for required reviewers: get the operator's decision (Enterprise, public, reviewers off with no approval gate, `AcceptDegraded`, or abort). Check: decision recorded in `docs/stack.md`. **Private repo on a Free account** (the common solo case): the script refuses by default. Recommend FIRST: make the repo public if nothing sensitive is in it, or buy GitHub Pro (rulesets; the approval gate still needs Enterprise or a public repo). If the operator knowingly stays private + Free, set `AcceptDegraded = $true`: the script applies what Free allows (Environments, variables, `main`-only branch policy, Dependabot) and prints a loud NOT ENFORCED list (no merge gate, no approval gate, no secret scanning, no CodeQL). The operator must accept that in writing and it goes into `docs/stack.md` (step 7). Never turn it on silently.
2. **Config + dry run.** Copy `templates/github/bootstrap.config.example.psd1` to `bootstrap.config.psd1`, fill owner, repo, `Plan`, reviewer logins. Run `powershell -File bootstrap-repo.ps1 -ConfigPath bootstrap.config.psd1` (or `pwsh -File ...`; dry run, no network). Check: every planned `gh` call is printed; show it to the operator.
3. **Apply.** With a clear yes, same command plus `-Apply`: private repo (default branch renamed to `main` first if the owner's initial-branch setting differs), squash-only merge with PR title, auto-delete branches, rulesets (`main` and `v*` tags), Environments `plan-dev plan-prod tf-dev tf-prod dev preview` (MainOnly ones are reconciled to exactly the default-branch policy: every other branch or tag policy is deleted and the final list verified), security switches, repo-wide variables, and the per-Environment variables that are already known. Check: exit 0, result table has no FAILED; second `-Apply` run changes nothing.
4. **First PR.** Work in a fresh clone or a git worktree placed outside the main checkout (never nested inside it), branch `chore/bootstrap`. Add CODEOWNERS, PR template, `dependabot.yml`, `SECURITY.md`, `ci.yml`, `pr-title.yml`, `release-please.yml` + config, `.gitattributes`, `.editorconfig`. PR title is a Conventional Commit. `ci.yml` passes before any app exists: every required job still runs and reports, and its package-dependent steps are skipped with a visible "no app yet" notice while there is no `package-lock.json`. Check: all 7 required checks run and pass; merge with `gh pr merge --squash`.
5. **Names match.** `python -I verify-required-checks.py ruleset-main.json ci.yml pr-title.yml` (`python3` on macOS/Linux). Check: `RESULT: OK`.
6. **Prove the repository-only gates red once** (`references/repo-bootstrap.md` section 10): G1 direct push to `main` rejected, G3 missing-check PR blocked, G7 non-conventional PR title blocked. Check: each shows the failure described there; clean up the proof branches/rulesets. Two proofs CANNOT run on Day 0 and are NOT skipped silently: G2 (failing-test PR blocked) needs an app test suite, G4 (`tf-prod` apply waits for approval) needs the Terraform/deploy workflows and cloud foundation. Record both in `docs/stack.md` as `pending, proven at step <section 4 scaffold | section 6 workflows installed>`.
7. **Record** (in `docs/stack.md`, dated): repo, plan, approvals decision (solo = 0 approvals, PR and checks still enforced), reviewers, the gates proven (G1, G3, G7) and the gates pending (G2, G4). If `AcceptDegraded = $true` was used: the full NOT ENFORCED list, the sentence "operator accepted private+Free degraded mode on <date>: no merge gate, no approval gate, no GitHub secret scanning", the exit plan (public repo or Pro, by when), and G1/G3/G7 as `NOT ENFORCED (degraded)`, never as proven.

Terraform, Cloud Run and WIF come next and plug into these Environments and variables.

### 3. PRD, spec, decisions
- `docs/prd.md` before implementation when requirements are open. Close open decisions only from user input or verified facts.
- Record security posture: OWASP review per feature, secret handling, admin auth boundary, data retention, least privilege.
- Pick the runtime: Cloud Run for request/response APIs and web apps (what the templates build). Anything else (always-on workers, socket gateways, static sites, admin-only UIs, background jobs): `references/optional-modules.md` ("Service selection"). Record the choice and reason in `docs/stack.md`.

### 4. Repo and scaffold
- Repo, `main` protection and base CI already exist from Day 0. Branches: `main` only (see section 7).
- Minimal scaffold for the chosen stack, `.gitignore` (include `*.tfstate*`, `.terraform/`, `tfplan`, `gha-creds-*.json`) and `.dockerignore` (`templates/docker/.dockerignore`), CI workflows, docs skeletons. No product features during scaffold.
- Push after the first clean scaffold. Once the app has a test suite and `ci.yml`'s `hashFiles` guards are gone: run proof **G2** (failing-test PR blocked), then update the `docs/stack.md` entry from pending to proven.
- Uncomment the stack's ecosystem in `.github/dependabot.yml` now that the manifest exists. Check: Dependabot shows no config error.

### 5. Terraform foundation (human runs once per environment)
1. Create **one GCP project per environment** (`<app>-dev`, `<app>-prod`) and link billing. This is required for isolation: `tf-applier-<env>` holds project-level roles, so in a shared project the dev applier could change prod resources. `bootstrap-repo.ps1` refuses identical `tf-dev`/`tf-prod` project ids unless `AllowSharedProject = $true`; if you accept that, record in `docs/stack.md` that dev and prod are NOT isolated.
2. Apply `templates/terraform/bootstrap/` **once per environment**, in that environment's project, with ADC (`gcloud auth application-default login`) and its own local state file: `terraform apply -var-file=dev.tfvars -state=dev.tfstate`, then the same for prod (`env.tfvars.example`). Each run creates: core APIs, the state bucket `<project>-tfstate-<env>` (versioned, public access prevented, `prevent_destroy`; one bucket per environment, so bucket IAM is the state isolation), the WIF pool `github-<env>` and provider, `tf-planner-<env>` (read-only, bound to GitHub Environment `plan-<env>`) and `tf-applier-<env>` (bound to `tf-<env>`, roles on that project only, state access on that bucket only). The dev run (`build_and_preview = true`) also creates `image-pusher` (bound to `dev`, NO project role) and `preview-deployer` (bound to `preview`). Prod gets neither. Keep the local state files (gitignored) and back them up.
3. Each WIF provider condition pins the numeric `repository_id`. Every identity is bound to ONE GitHub **Environment** subject (`repo:<owner>/<repo>:environment:<name>`), so a job outside that Environment cannot assume it. `preview` has no reviewers and runs PR code: its identity writes only the separate `api-preview` service and registry, never the dev or prod services.
4. Show each plan to the operator and get an explicit yes before the first `apply`. Never `-auto-approve` by hand.
5. Set the outputs as **Environment variables** (not repo-wide, not secrets), via the `Environments.<name>.Variables` blocks of `bootstrap.config.psd1` and a re-run of `bootstrap-repo.ps1 -Apply`: `plan-<env>`: `GCP_PROJECT_ID`, `WIF_PROVIDER`, `TF_PLANNER_SA`; `tf-<env>`: `GCP_PROJECT_ID`, `WIF_PROVIDER`, `TF_APPLIER_SA`; `dev`: `GCP_PROJECT_ID`, `WIF_PROVIDER`, `IMAGE_PUSHER_SA`; `preview`: `GCP_PROJECT_ID`, `WIF_PROVIDER`, `PREVIEW_DEPLOYER_SA` (all from the DEV bootstrap). Repo-wide: `GCP_REGION`, `TF_VERSION`. A job reads the variables of the Environment it runs in, so dev values can never leak into a prod job.
6. Per environment copy `templates/terraform/envs/dev` to `envs/prod` (a third environment such as `envs/staging` also needs its own bootstrap, GitHub Environments and an entry in the workflow `matrix.env` lists, which ship as `[dev, prod]`); set `backend.tf` to that environment's bucket and prefix (`envs/prod`), set **`env = "prod"`** in `terraform.tfvars` (it names the service `api-prod` and turns on `deletion_protection`), delete `preview_deployer_sa` and `registry_writer_sas`, pin `secret_version` to a number, and set sizing and ingress. Do not use workspaces for dev/staging/prod (Google's root-module guidance says to use only the default workspace; workspaces share one backend and hide differences). Copy `templates/scripts/tf-ci.sh` to `scripts/tf-ci.sh`. The service base name `api` is hardcoded in the env roots and the workflows: to rename it, change every place listed in `references/customizing-templates.md` ("Renaming the service") before the first apply.
7. Keep each state small (a few dozen resources, never >100). Split by service or layer when it grows.
8. **First apply, once per environment, by the operator** (this is what initializes the backend): `terraform -chdir=terraform/envs/<env> init`, then `apply -var image=us-docker.pkg.dev/cloudrun/container/hello` with the operator's ADC. Do prod first: the prod project's Cloud Run service agent only exists after that, and the dev tfvars then needs `registry_reader_members = ["serviceAccount:service-<PROD_NUMBER>@serverless-robot-prod.iam.gserviceaccount.com", "serviceAccount:tf-applier-prod@<PROD_PROJECT_ID>.iam.gserviceaccount.com"]` (the prod Cloud Run service agent AND the prod applier `tf-applier-prod`, output `applier_sa` of the prod bootstrap; Cloud Run needs repository access for both the deployer and the service agent) so prod can deploy and pull the dev-built digest (re-apply dev). Why not rely on CI: the GCS backend WRITES an empty state object when none exists, and the read-only planner cannot, so `plan` would fail on a fresh bucket. Then lock providers for CI's platform and every operator platform and COMMIT the lock file: `terraform -chdir=terraform/envs/<env> providers lock -platform=linux_amd64 -platform=<windows_amd64|darwin_arm64|...>`, commit `.terraform.lock.hcl`. Every CI init runs with `-lockfile=readonly`, so plan and apply use exactly the committed provider versions, and a missing or stale lock file fails the job instead of picking a newer provider between plan and apply. Check: `gcloud storage objects describe gs://<project>-tfstate-<env>/envs/<env>/default.tfstate` succeeds. The plan, apply and drift workflows run the same check first (`tf-ci.sh state-check`) and fail with a clear message if the object is missing.
9. State is sensitive: each bucket stays private and versioned, readable by its own planner and writable by its own applier and the operator only. GCS backend locks natively (no DB). `terraform force-unlock` only after confirming no run is active.

Resources by module (`templates/terraform/modules/cloud-run-service`): runtime SA per service, Artifact Registry repo with cleanup policies (KEEP the newest 20 versions, DELETE versions older than 90 days: KEEP alone deletes nothing; rollback window = 20 versions or 90 days, so redeploy or promote anything you still need to run), Secret Manager secret **containers** with per-secret `secretAccessor` for the runtime SA, and the Cloud Run v2 service (private by default, `deletion_protection` in prod, traffic 100% to the latest revision, image from `var.image`, NO `ignore_changes`). Repo grants: `artifactregistry.writer` for `registry_writer_sas`, `reader` for `registry_reader_members`. `modules/preview-service` creates the separate `api-preview` service, its runtime SA (no secrets) and registry; only there are revision fields under `ignore_changes`, because only `preview.yml` writes them. Secret IDs are namespaced `<service>-<env>-<NAME>` (for example `api-dev-DATABASE_URL`); the env var inside the container stays `DATABASE_URL`. Secret **values** never enter Terraform code or state, and mounting is **two-step**: (1) apply with `mount_secrets = false` (default) to create the empty containers, (2) add a version to each out of band (`gcloud secrets versions add <id> --data-file=-` from a temp file, or the console; `terraform output secret_ids` lists the IDs), (3) set `mount_secrets = true` in tfvars and apply again. Mounting before a version exists makes the instance fail to start.

After `terraform/envs/dev` exists, uncomment the `terraform` ecosystem in `.github/dependabot.yml`.

### 6. GitHub controls and CI/CD
- Environments (`plan-dev`, `plan-prod`, `tf-dev`, `tf-prod`, `dev`, `preview`) and the `main` ruleset already exist from Day 0 (reviewers on `tf-*`, `main`-only branch policy on `tf-*` and `dev`; "prevent self-review" off only for a solo operator, recorded in `docs/stack.md`). `tf-prod` must keep its reviewers. Here: once Terraform Plan exists, add it to the required checks through an always-running gate job (the plan job is path-filtered and a matrix, so requiring it directly would block PRs that do not touch `terraform/`).
- Copy workflows from `templates/github-workflows/` to `.github/workflows/` and `templates/scripts/tf-ci.sh` to `scripts/`:
  - `terraform-plan.yml`: same-repo PR, fmt/validate/plan per environment as `tf-planner-<env>` in Environment `plan-<env>`, `-lock=false`, with the image the service runs now, plan in the job summary.
  - `terraform-apply.yml`: THE deploy pipeline, push to `main`. `build` (Environment `dev`, `image-pusher`, token-only auth, skipped with a notice while there is no `Dockerfile`) pushes the image to the dev registry by digest; `plan` (read-only, per environment, saved plan + the image used) then `apply-dev` and `apply-prod` in Environment `tf-<env>` (**human gate**) apply the SAVED plan with `tf-applier-<env>`; `apply-prod` needs `apply-dev`, so prod runs only after dev applied and passed its digest check, never cancelled mid-apply. Then `tf-ci.sh verify` checks the traffic-serving revision runs the planned digest. A saved plan older than a state change is REFUSED as stale by Terraform: re-run for a fresh plan; the workflow-level concurrency group queues a newer push behind a run still waiting for approval. Both Terraform workflows set `shell: bash` (pipefail) and fail if `tfplan` is missing. The repo must carry a `.dockerignore` with `gha-creds-*.json` (template `templates/docker/.dockerignore`); the build fails otherwise.
  - `terraform-drift.yml`: weekday schedule as the planner, `plan -detailed-exitcode` (2 = drift; 0 = clean; ANY other exit code, 1 or 137 for example, fails the job), opens or updates one issue, never auto-applies.
  - `preview.yml`: per-PR tagged zero-traffic revision of the separate `api-preview` service (`--no-traffic --tag pr-N`), URL commented on the PR, tag removed on close (only a tag confirmed absent is ignored; any other failure fails the job), daily sweep for orphans (open PRs read with `--paginate`). Identity `preview-deployer` (Environment `preview`), which cannot write dev or prod.
- After these workflows are installed and the first dev apply has run: run proof **G4** (`tf-prod` apply waits for approval, only from `main`), then update the `docs/stack.md` entry from pending to proven.
- No workflow ever runs `gcloud run services update` against dev or prod: Terraform is the only writer, so there is no second deploy path to race with.
- Pin third-party actions; pin by commit SHA for anything that handles credentials. Keep `permissions:` minimal per job; only jobs that authenticate get `id-token: write`.
- App CI (`templates/github/ci.yml`: lint, typecheck, test, build, dependency-audit, secret-scan) comes from Day 0; delete its `hashFiles` guards when the app scaffold lands. For React-specific CI such as Playwright sharding or Storybook, extend `ci.yml` (keep the required job names, or make one aggregate job the single required check and update `ruleset-main.json`).
- Variables hold IDs and live on the Environment that uses them; real secrets stay in Secret Manager. Use GitHub secrets only when a workflow truly needs one.
- Anything "deployed" is checked per Principle 5: deploy job conclusion, serving-revision digest, env-var diff.

### 7. Branching and environments
- Default: trunk-based. `main` is the only long-lived branch; short-lived `feat/ fix/ chore/ docs/` branches (plus branches some AI coding tools create, e.g. `claude/`, same rules) merge into it by PR. PR title = Conventional Commit; release-please cuts `vX.Y.Z` tags, protected. Merge triggers plan then gated apply; the same commit is promoted dev then prod. Terraform state cannot be merged by git, so per-environment branches cause drift.
- Environments differ by directory (`envs/<name>`, own state bucket, WIF pool, identities and tfvars), not by code branch.
- Previews are Cloud Run revision tags on the separate `api-preview` service, not per-PR Terraform stacks and not revisions of the dev service. Destroy-on-close stacks are fragile and leak cost.
- If the operator insists on a long-lived `dev` branch: `dev` auto-plans, `main` applies, and record the reason in `docs/stack.md`. Warn that it doubles the merge work.

### 8. Secrets
- Placeholders in Secret Manager with the exact env names the code expects (via Terraform secret containers).
- Generate internal secrets locally and write them to Secret Manager from a temp file. Never show secret values in answers; docs hold names and resource IDs only.
- If a command prints a secret, rotate it and disable or destroy the exposed version.
- Do not mount a secret in Cloud Run until it has an enabled version (Cloud Run fails the deploy or the instance start): keep `mount_secrets = false` for the first apply, add versions, then set it true (section 5). Pin a version number in prod; `latest` only in dev.
- Per-secret access only. Never project-level `secretAccessor`.
- `.env`, `.env.local`, `*.tfstate*`, `tfplan`, `gha-creds-*.json`, generated credentials stay git-ignored (and `gha-creds-*.json` stays in `.dockerignore`). Plan artifacts can contain sensitive values: retention 1 day, never public.
- Before completion scan repo and logs for leaks; rotate before reporting done if one is found.

### 9. Runtime identity
- Separate runtime SA per service (the module does this; previews get their own with no secrets). Least practical permissions: secret accessor per secret, storage access scoped to one bucket. CI identities: `image-pusher` holds only `artifactregistry.writer` on the dev repo; `preview-deployer` only the `api-preview` service, its runtime SA and its registry; neither holds a project-level role. `tf-applier-<env>` is the only writer of the dev/prod services and holds project roles in its own project only (including project-wide `serviceAccountUser`, gated by the `tf-<env>` Environment). Service-level `run.developer` on `api-preview` is the narrowest Terraform can express; if a live preview deploy is denied `run.operations.get`, widen with an IAM condition, not a project-wide grant (not verified live yet).
- Avoid project-wide Owner, Editor, Storage Admin for runtimes. Remove default Compute SA grants and do not run apps as the default Compute SA.
- Cloud Run stays private by default (no `allUsers`). Verify with an unauthenticated request.

### 10. Verification
- Local gates before commit: `terraform fmt -check -recursive`, `terraform validate` per root, tflint/checkov if the repo has them, app tests.
- Open a PR with a trivial Terraform change; confirm the plan job is green and read-only (no lock, no state write).
- Merge; confirm `apply` paused at the Environment and applied the saved plan after approval. Check **job** conclusions and the serving-revision digest, not the run (Principle 5).
- Run `terraform plan` again: expect "No changes". Then confirm WIF auth, image push, Cloud Run health, bucket public access prevention, no public IAM members, and for any optional module in use its own checks (Firebase deploy only if intended, API key restrictions).
- Unauthenticated HTTP check on every public URL; record expected status.
- Update `docs/stack.md` with date, IDs, completed/pending, next infra task.

### 11. OWASP infra audit
Read-only after bootstrap: public endpoints, public IAM members, broad roles, default firewalls, secret access scope, bucket public access, API key restrictions, WIF conditions and Environment bindings, repo visibility/protection, DB allowlists, workflow exposure (who can trigger `id-token: write` jobs). Commands: `references/security-baseline.md` ("Audit an existing project"). Fix high-risk findings, then write `docs/infra-owasp-audit-YYYY-MM-DD.md`.

### 12. Security baseline (default for every project)
Checklist, Terraform snippets and audit commands: `references/security-baseline.md`. Treat each item as required; a skipped item is recorded in `docs/stack.md` as an accepted risk with date and exit plan. Items 1 to 4 apply only if the project uses MongoDB Atlas; items 5 to 9 and 12 always apply; item 10 applies to Firebase Hosting or any admin web UI; item 11 to shared service API keys. In short: own runtime SA with minimal roles, WIF with no JSON keys, per-secret IAM plus Secret Manager Data Access logs, locked-down buckets, alert policies and a budget, security headers, one revocable key per install, 2-Step Verification on owner accounts.

### 13. Optional modules
Only if the project uses them: `references/optional-modules.md` has service selection, GCP network hygiene (default VPC firewall rules, Compute Engine VMs), Firebase, Google auth, Gemini and MongoDB Atlas.

## Retrofit (project already has click-ops or gcloud infra)
Do not rebuild. For each existing resource: write the HCL, `terraform import` (or an `import {}` block), run `plan` until "No changes", then switch CI to the Terraform flow. Import read-only first, in a scratch directory, and show the operator the plan before it touches state. Secrets are never imported.

## Standard artifacts
`docs/prd.md`, `docs/stack.md`, `docs/deploy.md` (non-trivial deploys), `docs/ops-runbook.md` (VM or worker), `docs/infra-owasp-audit-YYYY-MM-DD.md`, `terraform/{bootstrap,modules,envs}`, `.github/workflows/{ci,pr-title,release-please,terraform-plan,terraform-apply,terraform-drift,preview}.yml`, `scripts/tf-ci.sh`, `.github/{CODEOWNERS,dependabot.yml,pull_request_template.md}`, `firebase.json` when Hosting is used.

## Completion bar
- Day 0 done: private repo (or a recorded plan decision; a degraded Free-private run counts only as "degraded, accepted on <date>" with its NOT ENFORCED list in `docs/stack.md`, never as fully done), `main` and `v*` rulesets active, squash-only merges, Environments with reviewers and `main`-only policy, security switches on, Dependabot and CODEOWNERS present.
- Gates proven red once, each at the earliest step that can run it: Day 0 G1 (direct push to `main` rejected), G3 (missing-check PR blocked), G7 (bad PR title blocked); G2 (failing-test PR blocked) once an app test suite exists; G4 (`tf-prod` apply waited for approval) once the Terraform/deploy workflows are installed. Any still pending is listed as such in `docs/stack.md`, never counted as proven. `verify-required-checks.py` says OK.
- PRD/stack docs current, no secrets in them.
- Bootstrap applied with operator approval; state in versioned GCS bucket.
- Plan on PR green, apply paused for a human and succeeded, second plan shows no changes, drift workflow ran once.
- WIF in use, no JSON keys exist; each environment has its own pool, bucket, planner and applier bound to its own GitHub Environment; `preview-deployer` bound to `preview` only and present only in the dev bootstrap; state initialized in every bucket (first apply done).
- Runtime SAs separate; broad default grants removed or justified.
- Security baseline (section 12) items done or recorded as accepted risks (Atlas items 1 to 4 only if Atlas is used); audit commands run once.
- Deploy proven at job and digest level (Principle 5).
